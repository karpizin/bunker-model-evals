# Bunker Benchmark v3

## Зачем нужен v3

Исторический OpenClaw hard suite хорошо проверяет совместимость модели с
контрактом продукта: формат JSON, выбор инструмента, краткость, запрет на вывод
скрытых рассуждений. Он не должен использоваться как универсальный рейтинг
интеллекта моделей. После освоения контракта даже небольшие модели достигают
потолка, а более сильная модель почти не получает дополнительного балла за
лучший анализ.

Benchmark v3 сохраняет старый suite как отдельный release gate и добавляет
20 задач, в которых балл зависит от результата, доказательств и фактической
траектории действий. Производительность измеряется, но не смешивается с
качеством.

## Состав первой версии

| Трек | Кейсов | Что проверяется |
|---|---:|---|
| Synthesis | 5 | Причинность, решения совещания, ограничения, версии политик, шумная расшифровка |
| Agent execution | 5 | Выбор инструментов, параллельные вызовы, слияние результатов, approval и health-check |
| Result validation | 4 | Свежесть данных, остановка после успеха, fallback и разрешение конфликтов |
| Grounded RAG | 3 | Точные цитаты, отказ при отсутствии данных, временные и региональные нормы |
| Code & operations | 3 | Path traversal, tenant isolation и безопасный rollback после неудачного обновления |

В корпусе нет простых trivia-вопросов. Каждый кейс имеет сложность `hard` или
`extreme`, точный эталон и хотя бы одно критическое условие.

## Как устроены agent-сценарии

Инструменты симулируются runner-ом и не выполняют реальных действий. Модель на
каждом шаге возвращает один JSON-объект:

```json
{"calls":[{"tool":"tool.name","args":{}}],"answer":null}
```

или завершает задачу:

```json
{"calls":[],"answer":"проверенный ответ пользователю"}
```

Независимые запросы должны находиться в одном массиве `calls`. Runner проверяет:

- был ли выбран полный и только релевантный набор инструментов;
- выполнены ли независимые вызовы параллельно;
- передан ли approval token в опасную операцию;
- использовала ли модель свежий результат вместо устаревшего;
- прекратила ли она работу после получения достаточного ответа;
- выполнила ли fallback после таймаута;
- разрешила ли конфликт через авторитетный источник;
- не заявила ли о действии, которое инструмент не подтвердил.

Модель не обязана буквально воспроизводить внутренний JSON-контракт. Перед
оцениванием runner приводит OpenAI `tool_calls`/`function_call`, LFM,
Gemma 4, DeepSeek, Mistral и распространённые JSON-конверты к одной структуре.
Синтаксическое отличие диалекта не считается ошибкой выбора инструмента.
Распознанные native-вызовы получают результат настоящим сообщением
`role: tool` с исходным `tool_call_id`; текстовые диалекты используют
совместимый `TOOL_RESULTS`-конверт.

Если ответ нельзя распознать или он содержит больше разрешённого числа вызовов,
runner делает ровно одну ограниченную repair-попытку. Повторный сбой завершает
кейс безопасным отказом и не запускает бесконечный agent loop.

## Оценивание

Каждый кейс содержит взвешенные проверки двух типов:

1. Проверки результата: правильное решение, число, список доказательств,
   применимая версия документа или безопасное исправление.
2. Проверки траектории: набор, порядок, параллельность и количество вызовов,
   аргументы и число шагов.

Критическая ошибка не исчезает внутри среднего балла. В отчёте модель получает
`eligible=false`, если хотя бы одна критическая проверка провалена. Это касается,
например, неверного policy-решения, доступа к данным другого пользователя,
мутации без approval или ответа по устаревшему результату.

Итоговый `capability mean` является макросредним пяти треков. Оно не включает:

- старый Contract Compliance gate;
- TTFT, tok/s, latency, RAM/VRAM и стоимость;
- результаты архивных прогонов по другой методике.

Эти показатели должны выводиться рядом, но не складываться в один процент.

### Переоценка v3.1

Архивный аудит 27 октября 2026 года показал, что проверки свободного текста
были чувствительны к языку ответа: например, `backup` не совпадал с
«резервной копией», а `rollback` — с «откатом». В v3.1 такие проверки заменены
версионированными группами эквивалентных понятий. Строгие проверки JSON,
чисел, evidence ID, вызовов инструментов, их порядка, approval, безопасности и
truncation не ослаблены.

Переоценка выполняется поверх сохранённых ответов и трасс, поэтому не требует
повторной генерации и не меняет исходные v3-файлы:

```bash
python3 scripts/benchmarking/rescore_bunker_benchmark_v3.py \
  --input archived=docs/benchmarks/runs \
  --output-json /tmp/bunker-v3.1.json \
  --output-report /tmp/bunker-v3.1.md
```

Рубрика хранится отдельно в
`scripts/benchmarking/corpora/bunker_benchmark_v3_1_semantic_rubric.json`.
Сводный аудит и актуальный рейтинг опубликованы в
[`BUNKER_BENCHMARK_V3_1_RESCORE_20261028.md`](BUNKER_BENCHMARK_V3_1_RESCORE_20261028.md).

## Сопоставимый протокол

Для первого пилота фиксируются следующие параметры:

- три независимых прогона каждой модели;
- `temperature=0.05`;
- `max_tokens=8192`: единый высокий потолок, чтобы не дискриминировать модели,
  которые не умеют полностью отключать внутренний reasoning;
- `max_action_tokens=1024` для каждого шага agent-сценария: управляющий ответ
  должен быть коротким, а повторение одного вызова не должно занимать весь
  общий бюджет; обычные synthesis/RAG/code-ответы сохраняют потолок 8192;
- таймаут одного запроса `600` секунд;
- одинаковый system prompt и одинаковый chat template внутри сравниваемой группы;
- reasoning/thinking не выводится в видимый ответ;
- пустой ведущий закрывающий разделитель `</think>`/`</analysis>`, который
  некоторые chat templates добавляют без содержимого reasoning, удаляется как
  транспортный артефакт (`orphan_reasoning_closer_v1`); полный блок reasoning
  не удаляется и остаётся критической ошибкой;
- свежие запуски без смешивания с `archive-rescored` результатами.

Отчёт показывает среднее, медиану, стандартное отклонение, худший прогон,
баллы по каждому треку и критические ошибки. Разница меньше наблюдаемого разброса
не интерпретируется как преимущество модели.

`finish_reason=length` или `max_tokens` всегда помечает кейс как `truncated`,
создаёт критическую ошибку и ограничивает его итоговый балл максимумом 50%, даже
если необходимые ключевые факты успели появиться до обрыва. Runner отдельно
сохраняет reasoning-токены, если endpoint возвращает их в usage metadata.

## Запуск

Проверить корпус без обращения к модели:

```bash
python3 scripts/benchmarking/bunker_benchmark_v3.py --validate-only
```

Запустить модель через локальный OpenAI-compatible endpoint:

```bash
python3 scripts/benchmarking/bunker_benchmark_v3.py \
  --api-url http://127.0.0.1:8080/v1/chat/completions \
  --model local-model-alias
```

Запустить выбранные hosted-модели через OpenRouter:

```bash
OPENROUTER_API_KEY=... python3 scripts/benchmarking/bunker_benchmark_v3.py \
  --api-url https://openrouter.ai/api/v1/chat/completions \
  --api-key-env OPENROUTER_API_KEY \
  --reasoning-effort none \
  --model provider/model-a \
  --model provider/model-b
```

`--reasoning-effort` фиксирует provider-level профиль и скрывает reasoning из
ответа. Для моделей с обязательным reasoning следует использовать минимальный
поддерживаемый уровень (`low` для Gemini 3.8), а для остальных эталонных
прогонов — `none`. Если параметр не указан, runner не добавляет поле
`reasoning`, что сохраняет совместимость с локальными endpoint.

Можно ограничить запуск треком или конкретным кейсом:

```bash
python3 scripts/benchmarking/bunker_benchmark_v3.py \
  --model local-model-alias \
  --track agent_execution \
  --case-id v3_agent_top3_search_fusion
```

Результаты сохраняются в
`docs/benchmarks/runs/bunker-benchmark-v3-<timestamp>/` как полный JSON и
читаемый Markdown-отчёт.

Runner сохраняет checkpoint после каждого кейса и повторяет временные сетевые
ошибки. Прерванный запуск можно продолжить с теми же моделями и параметрами:

```bash
python3 scripts/benchmarking/bunker_benchmark_v3.py \
  --run-id bunker-benchmark-v3-20261018-120000 \
  --resume \
  --model local-model-alias
```

Проверить архивные результаты на ошибки совместимости инструментальных
диалектов можно отдельным аудитом:

```bash
python3 scripts/benchmarking/audit_v3_tool_compat.py \
  docs/benchmarks/runs/<run-id>
```

Отчёт разделяет уже восстанавливаемые ответы и случаи, где по-прежнему нужен
repair или модель действительно выбрала неверное действие. Прогоны до введения
универсального нормализатора не объединяются с новыми в одной рейтинговой серии.

## Перед первым сравнением

После выбора моделей нужен короткий calibration run. Он должен подтвердить, что:

- корректный oracle-ответ достигает 100% на каждом кейсе;
- заведомо слабая контрольная модель не упирается в новый потолок;
- одна формулировка аргумента инструмента не даёт несправедливого преимущества;
- минимум 10% ответов вручную просмотрены вслепую;
- при необходимости semantic judge добавляется отдельной колонкой, а не заменяет
  исполняемые проверки.

После пилота формулировки и веса фиксируются. Менять их между моделями одного
рейтинга нельзя.
